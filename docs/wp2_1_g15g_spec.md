## 2. Threat statement (what is and is not bought)

Bought: a planted or edited `manifest.json` can no longer (i) point the loader at code **outside the plugin's own directory**, which is the only way to run code that the existing `*.py`-under-`ccos/plugins` HIGH classification (`core.checkpoint.is_core_file`) does not cover; (ii) win a plugin or capability name by directory order; (iii) spawn a process without a durable, attributable row.

Not bought, stated plainly: a manifest-write attacker can still set `process_spec.start_command` to any argv (F5, R1) and `process_spec.env` (`LD_PRELOAD`, `PYTHONPATH`); containment of `entry_point` does nothing for an external plugin that has a `start_command`. Blocking that is a manifest-write-classification matter (G15e) plus a policy decision (Q1), and the spawn row exists so the event is at least attributable. This is the same honesty bound the register applies to F3 ("hygiene plus truthful audit, not a boundary", consolidated section 7 F3(b)).

## 3. Design principles

1. **One helper, two call sites each.** A single module-level containment function is used at staging time (before any executable effect) AND again immediately before use (`exec_module` / `Popen`), and the **resolved** path is what is handed to `spec_from_file_location` / `Popen`, not the manifest string. Discovery-time state is never trusted at use time (the manifest dict and the filesystem can change between them).
2. **Refusal never falls through.** An escaping `entry_point` must refuse the load. It must not reach today's `exists()`-else-`__init__.py` fallback (`plugin_manager.py:704`); a test that merely asserts "nothing outside executed" would pass while hiding a missing refusal, so every containment test also asserts the refusal outcome, status and audit row.
3. **Ambiguity refuses everyone.** A name or capability with more than one claimant is refused for all claimants, deterministically (sorted walk), so an attacker who can add a manifest cannot win a name by iteration order. Cost: the same attacker can deny service to the genuine plugin; accepted (fail-closed; they could already corrupt it).
4. **Row authority convention.** Spawn rows (allowed, failed, pre-spawn refusal for operational reasons such as an existing PID record) use `ACT`, the class of the attempted action. Security refusals (containment, duplicate, collision) use `HIGH_IMPACT`, mirroring the existing refusal rows at `plugin_manager.py:994-1011`. No `coalesce_key` anywhere (refusals are never coalesced and spawns are rare; coalescing would hide a repeat spawn).
5. **No gateway API change.** `core/action_gateway.py` is not modified (G15e may be touching its classification, and rows already carry a free-text `command`). Consequence: the row cannot carry the pid (R8).

### 4.2 `_discover()` changes (`plugin_manager.py:581-610`)

1. Walk in **sorted** order at both levels (determinism; not itself a security property).
2. Directory/manifest symlink policy (decided here, option (a), to avoid a contradiction with step 4: an in-root symlink to another plugin dir would make one plugin appear twice and both copies would be refused as duplicates): **refuse any `category_dir`, `plugin_subdir` or `manifest.json` that `is_symlink()`**, even when its target is inside the root (F9: zero symlinks exist under `ccos/plugins` today, so this costs nothing), and additionally require `realpath(plugin_subdir)` inside `realpath(plugin_dir_root)` and `realpath(manifest_path)` inside `realpath(plugin_subdir)` (defense in depth against a symlinked **ancestor** of the root's children, which `is_symlink()` on the leaf does not see). Symlinked entry *files* inside a plugin dir remain allowed if they resolve inside (R6). On refusal **do not register**, append `{"path", "reason"}` to `self._discovery_refusals`, and write one `refuse_exec(authority=HIGH_IMPACT, action="ccos.plugin_discover:<dirname>", command=<path relative to root>, reason=...)`. (Covers symlinked plugin dir, symlinked category dir, symlinked manifest; F2.) Do not register a placeholder here: an out-of-tree manifest's `name` is untrusted.
3. Build claims `[(effective_name, path, manifest)]` where `manifest = normalize_manifest(json.loads(...))` is **the same object `Plugin.manifest` and `_stage_capabilities` use** (rule 12: `normalize_manifest` read in full, `manifest_schema_v2.py:309-356`: it copies the dict, leaves top-level `name` untouched, defaults `entry_point` to `"__init__.py"`, drops non-dict capability entries, and rewrites each capability to carry `id = cap.id or cap.name` and `name = cap.name or cap.id`, so after normalization a capability always has a `name` key and the `{plugin}.{id}` fallback at `plugin_manager.py:783` is reachable only if both are falsy, which then fails the `not cap_name` check). Name derivation is the **effective** name exactly as today (`manifest.get("name", plugin_subdir.name)`, including the directory-name fallback) and require `isinstance(name, str) and name.strip()` (an int/dict name is skipped as malformed, as unhashable ones already are).
4. Duplicate key = `unicodedata.normalize("NFKC", name).strip().casefold()` (stops `Agent`/`agent `/full-width tricks; module keys `ccos_plugin_{name}` and PID file names are case-sensitive strings, so near-duplicates are an impersonation vector, not just cosmetic). Keys with more than one claimant, **across all `plugin_dirs`** (single pass over the whole list, not per root), are refused: every claimant is registered as a placeholder `Plugin(name=<its exact name>, path=<its dir>, manifest={}, status=PluginStatus.DISABLED, error="refused: plugin name claimed by N manifests: <sorted relative paths>")` and one `HIGH_IMPACT` refusal row is written per distinct exact name. A placeholder never replaces a `Plugin` whose status is ACTIVE or whose name is in `self._activation_attempts` (a live lifecycle is never rewritten; this matters because `_discover` can be re-run, see R9).
5. Capability collision (4.4) runs after step 4 over the surviving claims.
6. Accepted claims are registered exactly as today (`Plugin(...)` assignment, same fields), so `list_plugins()`, `get_status()` shapes are unchanged except that `get_status()` gains `"refused": list(self._discovery_refusals)` (additive key) and DISABLED placeholders appear in `plugins`.
7. Re-discovery is idempotent: the duplicate test is per **pass** over fresh claims, so re-reading the same directory is never a "duplicate of itself" (tests in 7.1 call `manager._discover()` twice; `tests/test_plugin_activation_atomicity.py:62` already does).

### 5.1 Control flow (preserving every existing ownership/cleanup semantic)

Current order is: owned-handle fast path (339-352) -> resolve `cmd` (353-361) -> PID-record pre-check (362-369) -> env (370-372) -> `Popen` + store handle (374-379) -> publish PID, observe startup, health (380-392) -> `except Exception` cleanup (393-403). New order, same sequence:

1. Fast path unchanged: **no row** when an owned live child is returned (no spawn happened). The restart path (owned child dead, stopped, spawn again) **does** write a row.
2. `cmd` resolution (with 4.3 step 4). Compute `cwd`, `env, env_policy = _plugin_child_env(process_spec)` (5.3), and `audit_command = _spawn_audit_command(...)` (5.2).
3. Every **not-attempted** exit gets a `refuse_exec(authority=ACT, action=f"ccos.plugin_spawn:{plugin.name}", command=audit_command, reason=...)` row: unowned PID record (366-369, message and BROKEN status unchanged), missing entry (359-360), containment (already emitted by Unit A's 4.3 step 4 with `HIGH_IMPACT`; Unit B only keeps it single, it must not write a second row). Reason (advisor point, F11): on this device the stale live-state PID records mean the real spawn is refused before `Popen`, so a row wrapped only around `Popen` would never fire in production.
4. The spawn: `decision = get_action_gateway().gate_exec(authority=ACT, action=..., command=audit_command, confirm_available=False, execute=_spawn)` where `_spawn` does **only** `proc = subprocess.Popen(cmd, cwd=..., env=env, stdout=PIPE, stderr=PIPE)`, then `self._processes[plugin.name] = proc; plugin.pid = proc.pid`, then `return proc`. Assigning the handle inside the thunk is load-bearing: it keeps ownership recorded atomically with the child's existence, so if the gateway raises after the thunk (non-`OSError` audit failure; `gate_exec` only catches `Exception` around `execute`, 498-515) the existing `except Exception` cleanup at 393-403 still finds and stops our owned child.
5. Branch on the outcome: `OUTCOME_FAILED` (Popen raised, e.g. `FileNotFoundError`, no handle stored) => `raise RuntimeError(decision.reason)` into the **existing** `except Exception` so status/`plugin.error="External process startup failed"`/`return False` are byte-identical to today; `OUTCOME_ALLOWED` => `proc = decision.detail["result"]` and continue with `_publish_pid` etc. unchanged. `OUTCOME_REFUSED` cannot occur for ACT but must be handled as failure for safety.
6. The `Popen` call keeps resolving `subprocess.Popen` through the module attribute at call time: existing tests monkeypatch `module.subprocess.Popen` (`ccos/tests/test_process_supervisor_ownership.py:62-69,102,166,191`, `ccos/tests/test_external_plugin_supervision.py:34-41`).

The supervisor `RLock` is held across the thunk and the single file append; the gateway takes no lock for ACT without a coalesce key, so there is no new lock-order edge.

### 5.2 Row content (`_spawn_audit_command`, pure, unit-tested)

One line, `key=value` pairs, JSON for lists: `plugin=<name> mode=<execution_mode> cwd=<cwd> argv=<shlex.join(cmd), truncated at 512 chars> argv_sha256=<first 16 hex of sha256 of the full joined argv> env_policy=<inherit-all|...> env_override_keys=<sorted names from process_spec.env> cred_like_env_names=<sorted names of the child's env keys matching (?i)(KEY|TOKEN|SECRET|PASS|CRED|AUTH|COOKIE), capped at 20>`. **Never environment values**; the cred-like list is a documented heuristic (no completeness claim, G15h owns the real allowlist). Evidence: on this session's env 1 of 62 names matches (`CLAUDE_CODE_MESSAGING_TOKEN`), and the register's own C:M06 example (`OPENROUTER_API_KEY`, `AIGENTIK_INTERNAL_TOKEN`) matches. Argv can itself carry secrets (NEW-1033 / G15h class); the row follows the precedent of the shell rows, which record full command text, and the truncation + hash bound the exposure. State this in the ledger.
