## 2. Which ops the graphs actually use

qwen35 uses **`GGML_OP_SSM_CONV` + `GGML_OP_GATED_DELTA_NET`**, NOT `GGML_OP_SSM_SCAN` (`grep -c ggml_ssm_scan` = 0 in `qwen35.cpp`
and `delta-net-base.cpp`). Recurrent layer (qwen35.cpp:349-482): MUL_MAT (wqkv, gate, beta, alpha, out), SIGMOID, ADD, SOFTPLUS, MUL,
GET_ROWS (`build_rs`), CONCAT, CPY (conv + ssm state write-back, delta-net-base.cpp:449-525), SSM_CONV, SILU, RMS_NORM+SCALE
(`build_gdn_l2_norm`, models.h:14 -- it is NOT `GGML_OP_L2_NORM`), then `build_recurrent_attn`.

`build_delta_net` (delta-net-base.cpp:425-447) has three variants, selected at runtime:
- fused: single `GGML_OP_GATED_DELTA_NET` (n_tokens==1 -> "AR", else "CH"); default `fused_gdn_ar/ch = true` (llama-context.cpp:235-236);
- unfused autoregressive (n_tokens==1): EXP, MUL, SUM_ROWS, SUB, REPEAT, ADD, SCALE, PERMUTE;
- unfused chunked: CUMSUM, TRI, DIAG, SOLVE_TRI, PAD, CONCAT, MUL_MAT, EXP, ...
- when `n_rs_seq > 0` the graph uses `ggml_gated_delta_net(..., K = n_rs_seq+1)` (delta-net-base.cpp:567); default `n_rs_seq = 0` (llama-context.cpp:3832) => K=1.

Attention layers: MUL_MAT, RMS_NORM, ROPE (`ggml_rope_multi`, rope type IMROPE for QWEN35, llama-model.cpp:3207-3213), SET_ROWS (KV write),
FLASH_ATTN_EXT (or MUL_MAT+SOFT_MAX), SIGMOID, MUL. Codey-OS passes `--flash-attn on` to the main server (`core/loader_v2.py:764-765`).

nomic-bert: NORM (LLM_NORM, with bias -> ADD/MUL), ROPE (NEOX, llama-model.cpp:3127..3193), FLASH_ATTN_EXT or MUL_MAT+SOFT_MAX with an
unpadded n_tokens x n_tokens mask (`build_attn_inp_no_cache`, llama-graph.cpp:2832), SILU/MUL (FFN), GET_ROWS (embeddings), MUL_MAT (mean pooling,
llama-graph.cpp:3831). **There is no separate "non-causal attention op".** Causality is only the *contents* of the mask tensor
(`set_input_kq_mask(..., cparams.causal_attn)`, llama-graph.cpp:514/544), filled host-side. Verified by reading, not just grepping: `htp/flash-attn-ops.c` iterates ALL KV blocks `ic_start = ib*BLOCK .. nek1` (lines 315-353, 2127-2173, no q-position vs kv-position block skipping) and applies the mask
only as values (`mask > -16.0` keep, else -inf, :1261-1284); an all-zero mask therefore attends bidirectionally, an upper-triangular -inf mask is causal. So the question reduces to whether
FLASH_ATTN_EXT / SOFT_MAX / MUL_MAT pass their gates for nomic shapes.
Codey-OS embed server (`core/embed_server.py:215-231`) passes `-c 2048 -b 2048 --ubatch-size 2048 --embedding --pooling mean`, no `--flash-attn`,
so FA = default AUTO (`common/common.h:504`, resolved by probe at `llama-context.cpp:559`).

## 4. Runtime placement and "silent fallback" mechanisms (what to check later)

1. Fused GDN can disable itself: `llama-context.cpp:520-593` builds a reserve graph, and if the fused node's backend device != the layer's device it logs
   `fused Gated Delta Net (autoregressive|chunked) not supported, set to disabled` and `fused_gdn_*=false` -> the **unfused** chunked/AR graph is used,
   which then needs the longer op list in row 3a. That is a silent-ish §10.3 fallback; the log line `... enabled` vs `... not supported` is the discriminator.
2. Per-node verdicts: `GGML_HEXAGON_VERBOSE=1` makes `ggml_hexagon_dump_op_supp` print `supports-op <op>|names|dims|types|strides|buffs|yes/no` (P:174, called P:8672).
3. Force-switch knobs (P:9060-9082): `GGML_HEXAGON_GDN_SELECT` (0 = CPU, 1 = HVX, 2 = HMX->HVX), `GGML_HEXAGON_FA_SELECT`, `GGML_HEXAGON_OPFILTER` (regex deny-list), `GGML_HEXAGON_PROFILE`.
4. Standalone per-op test on real silicon with no model: the existing `.work-npu/build/bin/test-backend-ops` (Oct 8) -- the e358d59 source has `GATED_DELTA_NET`
   and `SSM_CONV` cases (tests/test-backend-ops.cpp:4403, 4696; realistic GDN configs near :11813). Command to propose (NOT run): `test-backend-ops -b HTP0 -o SSM_CONV` and `-o GATED_DELTA_NET`, `-o FLASH_ATTN_EXT`.
5. Existing empirical (not placement) evidence: OPENCL_PERFORMANCE_ANALYSIS.md:401 "recurrent Qwen3.5-4B also completed a full-offload smoke test" and :434
   "Qwen3.5 recurrent 4B, FAOFF: top-token agreement 32/32, RMSE 0.470, max abs logit diff 9.02, mean KL 1.756e-4". That proves it ran end to end on e358d59, FA off, and was numerically
   close in a 32-token forced-prefix test -- it does **not** show where each op ran (the same repo says "layer assignment is not proof of exclusive execution", README.md:353). I found no log line
   mentioning Gated Delta Net / fused_gdn in any report/log (grep of `reports/`, `.work-npu/logs/`, `execution_history.log`, `docs/` returned nothing).
   Also note: logits are explicitly "not bit-identical" to CPU (docs/NPU_INSTALL.md "Performance and limitations") -- see WP3.0b gate wording below.

## 6. Caveats and corrections

1. **Static gate != execution.** Every YES above is "the host gate accepts the shapes derived from the GGUF and a DSP kernel exists in the built library". Where each node
   really ran is unverified (forbidden here). The authoritative discriminators are in section 4.
2. **Two trees.** The only tree ever compiled for HTP is e358d59; Codey-OS pins 4f540676. Gates are identical for the ops in question, but the DSP `.so` for 4f540676 has never been built or inspected (the pin's `htp/main.c:910/943` and `CMakeLists.txt:26,37` do include the kernels).
3. **`mmap_support=false` / `-lm mmap` is mandatory** (above).
4. **Single DSP session ceiling** (`0x200` AEE_ERPC on session 1; OPENCL_PERFORMANCE_ANALYSIS.md / reports/2026-10-05/NEXT_WORK.md) still applies: qwen35 + nomic + planner concurrently cannot each hold an HTP0 session. This is not an op-support finding but it caps what "supported" is worth for Codey (blueprint §22 item 3).
5. **ISSUE FOR ISH (not an architect edit): WP3.0b's "identical output" gate looks unachievable as worded.** The OpenCL repo documents NPU logits as not bit-identical to CPU (Qwen3.5 4B: max abs diff 9.02 even with 32/32 top-token agreement). Changing a roadmap gate needs Ish's logged decision. Candidate wording to put to him: (a) state-copy integrity: byte-equality of the attention-KV and recurrent-state buffers immediately before vs after migration; (b) end-to-end: NPU-prefill/CPU-decode vs full-CPU top-token agreement and KL within a pre-registered bound (existing `.work-npu/build/bin/compare-cpu-htp-logits` already does the CPU-vs-HTP logit comparison). A same-backend "un-migrated vs migrated" test is not well-defined for a one-way NPU->CPU handoff.
6. **HMX GDN layout**: the gate would return NO on VTCM failure with no HVX fallback inside it, but at the recorded `vtcm 8 MB, threads 4` it solves (3c). Re-check if the session's reported VTCM/threads ever differ (e.g. `GGML_HEXAGON_NHVX`).
7. FA is VTCM-safe via the HVX fallback (3c). The residual nomic risk is the FA-off path: the softmax `ne0%32` trap. Also FA gate rejects `dst->ne[3]!=1` (multi-stream cache).
8. WP3.4 "`-DLLAMA_BUILD_SERVER=OFF` today" is true of the scripts (`build-npu.sh:66`); the `.work-npu` cache was later hand-reconfigured to ON and a server wrapper exists (see survey). Not a blueprint error; just note that an HTP llama-server build has been done once manually.
9. `ggml_hexagon_supported_rope` explicitly rejects a degenerate dummy rope (loader probe) so rope_freqs does not land on CPU (P:7150) -- irrelevant to op support but explains graph-split behaviour.
10. Pre-existing dirty state in `~/OpenCL-S24-Ultra` (` M .gitignore`, untracked `.work-opencode-runtime/`, `bin/`) noted; nothing was touched.
