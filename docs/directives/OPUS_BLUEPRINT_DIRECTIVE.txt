
CODEY-OS OPUS MASTER BLUEPRINT DIRECTIVE
Repository Census • Architecture Reconciliation • Cleanup • NPU Integration • Complete Developmental Roadmap
This document tells Opus how to discover and construct the definitive blueprint. It is not itself permission to blindly implement assumptions.
1. Assignment
Opus is to perform a comprehensive read-only architectural census of the current Codey ecosystem and then construct ONE authoritative, implementation-ready master blueprint for completing Codey-OS. The blueprint must reconcile what already exists, unfinished work, dormant systems, duplicate/dead code, companion repositories, current agent workflow, NPU/inference work, developmental goals, production constraints, testing, migration, cleanup and documentation.
Do not begin the large implementation program while constructing the blueprint. First understand the system well enough that the blueprint is based on reality rather than old plans.
2. Ultimate Objective
Codey-OS is a persistent developmental AI architecture, not merely an LLM wrapper and not a claim that AGI has already been designed. The system should be capable of accumulating verified experience, memory, skills and developmental history; becoming progressively less teacher-dependent; generating bounded practice and curiosity; safely testing improvements; and replacing or enlarging its underlying neural brain without losing the larger system's accumulated development.
The neural model is a replaceable brain, not Codey's identity.
The whole system is the research object.
Learning and improvement require measurable evidence.
The architecture must support continued growth without requiring a future large model to exist today.

5. Absolute Restoricon Production Rule
Restoricon must remain operational while Codey development proceeds. Development must fail around Restoricon; Restoricon must never fail because Codey is experimenting.
Do not stop, restart, disable, replace, migrate, reconfigure or repurpose live Restoricon processes/services/databases/ports/deployments merely for Codey work.
Do not knowingly consume shared CPU, RAM, storage, battery, network or other resources in a manner that threatens Restoricon availability.
Do not use live Restoricon data as developmental Playground data.
Use mocks, fixtures, staging or read-only interfaces wherever possible.
Any genuine production migration, schema change, deployment change, credential change or destructive production write is a separately identified maintenance action requiring Ish's explicit approval.
Production secrets never enter teacher prompts, developmental logs, training datasets or public repositories.
Map current production dependencies before planning integration work; include health checks, rollback and compatibility tests.
No autonomous agent may expand its own Restoricon privileges.
6. FIRST PRIORITY: NPU Integration Into Codey-OS
OpenCL-S24-Ultra now contains a separately validated Hexagon v75 NPU path and experimental NPU-prefill/CPU-decode work. Treat NPU integration as the first major technical architecture priority after the census, but do not hard-code NPU as universally superior.
Create/complete a backend-independent BrainManager / inference adapter boundary in Codey-OS.
Integrate the validated NPU path as a selectable backend.
Preserve CPU as known fallback/baseline.
Support phase-aware execution such as NPU prefill -> CPU decode where validated.
Keep OpenCL GPU available as experimental/research backend.
Record per-model/per-context/per-workload compatibility and performance rather than assuming all GGUFs work equally.
Resource policy should consider RAM, context, battery, temperature, CPU/NPU/GPU availability and workload phase.
Do not copy unstable research patches into cognitive code; integrate through a stable backend contract.
Benchmark exact deployed Codey models before changing production defaults.

9. Codebase Cleanup and Structural Refactoring Mandate
The roadmap must include continuous cleanup. Do not postpone all technical debt until the end.
Identify dead/unreachable code with evidence before deletion.
Identify duplicate implementations and choose one canonical path.
Remove superseded compatibility shims when no supported caller requires them.
Consolidate repeated utilities/configuration/schema definitions where doing so reduces real maintenance burden.
Repair misleading names and obsolete comments.
Restructure the Codey-OS directory tree when current placement obscures subsystem ownership or causes circular/duplicate architecture.
Separate core interfaces from adapters/integrations where useful.
Move tests with or near their logical subsystem according to the chosen project convention.
Update imports, manifests, startup scripts, configuration, tests and canonical documentation in the same structural change.
Perform refactors in bounded batches with tests and rollback commits.
Do not mix large behavioral changes and massive file moves when they can be separated.
Preserve git history as reasonably as possible through moves/renames.
Never delete code merely because it appears unused from one search; inspect dynamic imports, plugins, shell entry points, services and external callers.
Before removing legacy code, state what replaces it and how equivalence is verified.

14. Learning and Verification Principles
Experience is not learning until it measurably changes future behavior.
Canonical trajectories remain complete; display/export truncation is separate.
Durable skills/training data require appropriate external verification.
Teacher models provide candidate guidance, not unquestioned truth.
Model-independent skills/memory should survive brain swaps.
Sleep/consolidation may replay, deduplicate, cluster failures, extract procedures and prepare verified datasets.
LoRA/SFT is a slower consolidation mechanism, not Codey's only memory.
Curiosity should emphasize learning progress rather than raw novelty.
Self-improvement follows hypothesis -> isolated candidate -> benchmark -> regression/safety check -> promote/reject -> record -> rollback capability.
Retain both architectural scoring and Developmental Index measurements: growth/exposure, sample efficiency, retention, transfer, teacher dependence, self-directed improvement, calibration, breadth and zero safety violations.
