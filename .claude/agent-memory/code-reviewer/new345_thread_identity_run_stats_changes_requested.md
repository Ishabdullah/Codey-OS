Round 1 review of the NEW-345 fix (per-OS-thread-identity keying, `_RUN_STATS_BY_THREAD` replacing the single shared `_LAST_RUN_STATS` dict) in `core/agent.py` + `core/task_executor.py`. Verdict: CHANGES REQUESTED, doc-only.

**Design verified sound.** ThreadPoolExecutor's default executor (no custom executor installed anywhere — checked) never runs two callables concurrently on the same OS thread, so keying stats buckets by `threading.get_ident()` genuinely isolates an orphaned (timed-out, still-running) `run_agent()` call from a freshly-dispatched one. All three `setdefault`-based write helpers (`_set_run_stat`/`_incr_run_stat`/`_incr_run_stat_tool`) plus `get_last_run_stats()`'s `.get("tools_called", {})` make KeyError impossible under any ordering. Lock scope covers pop+copy atomically. All 3 recursive tail-call sites in agent.py (`return run_agent(_follow_up, ...)`) confirmed genuine tail calls, matching the docstring's honest reentrancy carve-out.

**Negative-control technique that mattered here**: the new regression test (`test_orphaned_thread_never_corrupts_concurrent_tasks_stats` in `tests/test_task_executor_telemetry.py`) can't be tested against pre-fix code by reverting (the helper functions it calls, `_reset_run_stats`/`_set_run_stat`, don't exist pre-fix). Instead: backed up `core/agent.py` to scratchpad, monkey-patched all 4 thread-aware functions to key on a constant `0` (simulating the old shared-dict design) in place, reran the specific test — it failed exactly as predicted (`assert 999 == 2`, A's late write corrupted B's bucket). Restored from the scratchpad backup, confirmed `git diff` byte-identical after restore. This is the cleanest way to prove a *newly-added* regression test is load-bearing when there's no real "revert and rerun" option — reusable pattern, see [[git_checkout_path_wipes_uncommitted_diff]].

**Required fix**: `core/task_executor.py`'s comment on `_worker_thread_id` overclaims. It says an empty `_worker_thread_id` list at `finally`-check time "correctly means the callable never started executing." False in a real window: cancellation can land between the executor picking up the callable and the callable's first line (`_worker_thread_id.append(threading.get_ident())`) actually running — the callable *has* started, just hasn't published its id yet. Safety-benign (no cross-task corruption results, only a completeness loss in that task's own telemetry + a latent orphaned-bucket leak if the pool is saturated), but the causal claim in the comment is factually wrong — same class of issue that blocked T8a round 1 ([[t8a_daemon_dedup_docstring_overclaim]]). Required wording: "empty means this call had not yet published its worker thread id — either never dispatched, or dispatched but cancelled before the callable's first line ran."

**Non-blocking findings logged**: (1) NEW_ISSUES.md's NEW-345 entry not yet updated to reflect the fix — expected at this stage, ledger updates are coordinator step 5 post-approval, not a defect. (2) Rule-8 candidate worth a NEW_ISSUES.md line (Suspected): each timed-out task permanently occupies one executor worker thread for the duration of the orphaned run_agent() call — pre-existing thread-pool-starvation risk, not introduced by this diff, but is what makes the required-fix window above non-theoretical. (3) `_seq_before = None` dead variable, implementer self-flagged — Suggestion, delete don't keep-with-comment. (4) New test's cleanup (`del _RUN_STATS_BY_THREAD[...]`) runs after assertions not in `finally` — harmless (fixed sentinel key) but inconsistent with the new race test's own finally-based cleanup.

Independently reran full suite: `1410 passed, 1 skipped in 176.12s` — matches implementer's claim exactly. Reran the specific telemetry test file 5x for flakiness — 8/8 passed every time, all synchronization via bounded (`timeout=5`) `threading.Event`, no sleep-based timing.
